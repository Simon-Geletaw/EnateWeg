## 1. What is YeEnat Weg?

**YeEnat Weg** (Amharic: *"Mother's Way / Mother's Tradition"*) is a mobile-first wellness
platform built for the Ethiopian context. Most diet and nutrition apps assume Western foods,
Western eating patterns, and a user who reads English. YeEnat Weg flips that: it is built
around **Ethiopian cuisine**, **Amharic-first localization**, and **locally-relevant health
realities** such as Orthodox/Ramadan fasting and the rising prevalence of diabetes and
hypertension.

The product takes a short health questionnaire and produces:

- A **personalized 7-day meal plan** of Ethiopian dishes, sized to the user's calorie and
  macro targets and filtered by their dietary rules (fasting, vegetarian/vegan, allergies).
- A **lifestyle suggestion** — a recommended sleep window and a few realistic exercises.
- A **daily logging experience** so users can record what they actually ate (whether they
  followed the plan or substituted their own meal), their water intake, and — for users with
  diabetes — their **blood-sugar readings**, which feed back into the plan.

The differentiator is the **feedback loop**: the plan is not static. When a diabetic user logs
an out-of-range blood-sugar reading, the system regenerates the plan with tightened
carbohydrate and sugar targets.

## 2. The Core Idea: Meal = Ingredients

The whole data model rests on one principle:

> **A meal is a named set of ingredients with quantities.**
> *e.g. "Oats with eggs" = Oats 100 g + Eggs 250 g.*

Each **ingredient** stores nutrition per 100 g (calories, protein, carbs, fat, fiber, sodium,
sugar, glycemic index) plus dietary flags (fasting-safe, vegetarian, vegan). A **meal**
aggregates the nutrition of its ingredients.

This single `ingredients → meal_items → meals` structure is reused in two places:

```
ingredients ──< meal_items >── meals ──┬── meal_plan_slots   (what the AI planned)
                                       └── meal_logs          (what the user actually ate)
```

- **Planned meal** — generated by the AI and attached to a slot in the weekly plan.
- **Logged meal** — what the user actually consumed. If they *followed* the plan, the log points
  at the planned meal. If they *substituted*, the user inserts the ingredients they really ate,
  which creates a brand-new logged meal with its own computed nutrition.

This keeps planning and logging perfectly symmetrical and makes "I ate something different"
a first-class, fully-nutrition-tracked action rather than an afterthought.

## 3. Key Features

| Area | What it does |
|---|---|
| 📱 **Phone (OTP) authentication** | Passwordless login via one-time code; stateless JWT access tokens + rotating refresh tokens. |
| 🧑‍⚕️ **Health profiling** | Captures sex, age, body metrics, activity, goal, fasting type, diet rules, allergies, and medical conditions. |
| 🧮 **Automatic targets** | Computes daily calories (Harris–Benedict BMR × activity, adjusted for goal) and macro/sodium/sugar targets, tightened for diabetes & hypertension. |

| 😴 **Lifestyle suggestions** | A sleep window plus exercise recommendations generated alongside each plan. |
| 🍽️ **Meal logging** | Log a planned meal as "followed" or insert your own ingredients as "substituted." |
| 💧 **Water & readings** | Daily water tracking and blood-sugar / blood-pressure readings. |
| 🔁 **Adaptive re-planning** | High fasting blood sugar → plan regenerates with lower glycemic load. |
| 🌍 **Bilingual (am / en)** | Amharic-first content and error messages, English fallback. |
| 📖 **Self-documenting API** | Interactive Swagger UI at `/v1/docs`. |

## 4. How It Works — The End-to-End Loop

```
1. Register / Log in     POST /v1/auth/otp/verify            → JWT tokens, is_new flag
2. Build health profile  PUT  /v1/users/me/health-profile    → targets + AI plan + lifestyle
3. View the plan         GET  /v1/meal-plans/current/weekly   → 7 days of meals + ingredients
4. Log meals             POST /v1/logs/daily/{date}/meals     → followed OR substituted
5. See the dashboard     GET  /v1/logs/daily/{date}           → consumed vs. target, alerts
6. (Diabetic) log sugar  POST /v1/health-readings             → plan auto-updates if out of range
7. Repeat weekly         POST /v1/meal-plans/generate         → fresh plan on demand
```

The moment a user saves their health profile, the backend computes their nutrition targets and
**immediately generates and persists a full meal plan** in the same request (gracefully
degrading if the AI service is unavailable — the profile is still saved).

## 5. Architecture

YeEnat Weg is a **monorepo** with two independently-runnable applications:

```
┌────────────────────────┐         HTTPS / JSON          ┌────────────────────────────┐
│   client/  (Expo RN)   │  ───────────────────────────▶ │   server/  (Express API)   │
│  React Native mobile   │   Bearer JWT, Accept-Language  │  REST · /v1 · TypeScript   │
│  app — screens, store, │ ◀───────────────────────────  │                            │
│  i18n, navigation      │                                └─────────────┬──────────────┘
└────────────────────────┘                                              │
                                                          ┌─────────────┴──────────────┐
                                                          │   PostgreSQL (Neon cloud)   │
                                                          └─────────────────────────────┘
                                                                        │
                                                          ┌─────────────┴──────────────┐
                                                          │   Google Gemini (AI plans)  │
                                                          └─────────────────────────────┘
```

**Backend request flow:** `Route → authenticate (JWT) → validate (Zod) → controller →
service / DB → errorHandler`. Cross-cutting concerns (auth, validation, error shaping,
localization) live in middleware so controllers stay thin.

## 6. Tech Stack

### Backend (`server/`)
- **Runtime:** Node.js + **Express 5**, written in **TypeScript** (run with `tsx`).
- **Database:** **PostgreSQL** via `pg` (hosted on **Neon**).
- **Auth:** `jsonwebtoken` (stateless access tokens), hashed opaque refresh tokens, `bcryptjs`.
- **Validation:** **Zod** schemas via a reusable `validate()` middleware.
- **AI:** **Google Generative AI** (`@google/generative-ai`, Gemini models).
- **Security/ops:** `helmet`, `cors`, request logging.
- **Docs:** `swagger-jsdoc` + `swagger-ui-express`.

### Frontend (`client/`)
- **React Native** with **Expo** (SDK 51).
- **Navigation:** React Navigation (native-stack + bottom-tabs).
- **State:** **Zustand** with AsyncStorage persistence.
- **Networking:** **Axios** (auto-detects dev host; falls back to `10.0.2.2` on Android emulator).
- **i18n:** `i18next` / `react-i18next` (Amharic + English).

## 8. Getting Started

### Prerequisites
- **Node.js ≥ 18** (tested on Node 24) and **npm**.
- A **PostgreSQL** database. The project is configured for **Neon** (cloud); a local Postgres
  works too — just point `DATABASE_URL` at it.
- *(Optional, for AI plans)* a **Google Gemini API key** from [Google AI Studio](https://aistudio.google.com/).
- *(For the mobile app)* the **Expo** toolchain / Expo Go app.

### 8.1 Run the backend

```bash
cd server
npm install

# Configure environment
cp .env.example .env          # then edit .env with your DATABASE_URL, JWT secrets, GEMINI_API_KEY

# Create the schema (tables + seed medical conditions)
npm run migrate

# Start the API in watch mode
npm run dev
```

You should see `✅ Database connected successfully` and a banner on **port 3000**.

Smoke-test it:

```bash
curl http://localhost:3000/v1/health
# → { "status": "ok", "service": "YeEnat Weg API", ... }
```

Open the interactive API docs: **http://localhost:3000/v1/docs**

> **Production build:** `npm run build` (compiles to `dist/`) then `npm start`.

### 8.2 Run the mobile client

```bash
cd client
npm install
npm start            # Expo dev server  (or: npm run android | npm run ios | npm run web)
```

The client auto-detects your dev machine's host for the API base URL. On the Android emulator
it falls back to `http://10.0.2.2:3000/v1`; on web/localhost it uses `http://localhost:3000/v1`.
Make sure the backend is running first.

## 9. Configuration (Environment Variables)

All backend config lives in `server/.env` (see `server/.env.example`):

| Variable | Required | Description | Example / Default |
|---|---|---|---|
| `PORT` | no | HTTP port | `3000` |
| `NODE_ENV` | no | Environment mode (enables dev request logging) | `development` |
| `DATABASE_URL` | **yes** | Full Postgres connection string (Neon needs `sslmode=require`) | `postgresql://user:pass@host/db?sslmode=require` |
| `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` | no | Discrete DB fields (fallbacks if `DATABASE_URL` unused) | `localhost` / `5432` / `yeenat_weg` |
| `JWT_SECRET` | **yes** | Signing secret for access tokens | — |
| `JWT_REFRESH_SECRET` | **yes** | Secret for refresh-token flow | — |
| `JWT_EXPIRES_IN` | no | Access-token lifetime | `15m` |
| `JWT_REFRESH_EXPIRES_IN` | no | Refresh-token lifetime | `7d` |
| `GEMINI_API_KEY` | for AI | Google Gemini API key (meal-plan generation) | — |
| `GEMINI_MODEL` | no | Gemini model id | `gemini-2.5-flash` |

> ⚠️ **Security:** never commit real secrets. Add `server/.env` to `.gitignore` and rotate any
> credentials that have been shared. If `GEMINI_API_KEY` is missing/invalid, every endpoint still
> works **except** AI meal-plan generation, which fails gracefully.

## 11. Data Model

PostgreSQL schema (created by `server/src/db/migration.sql`). Core tables:

| Table | Purpose |
|---|---|
| `users` | Accounts (phone / Google), name, language, soft-delete. |
| `otp_sessions`, `refresh_tokens` | Auth — one-time codes and long-lived refresh tokens. |
| `health_profiles` | One per user. Metrics, goals, diet rules, **computed targets**, BMI (generated column), `profile_version`. |
| `medical_conditions`, `user_conditions` | Supported conditions (diabetes T1/T2, hypertension) and the user↔condition link. |
| `ingredients` | Ethiopian food DB — nutrition per 100 g + dietary flags + serving helpers. |
| `meals`, `meal_items` | A meal and its ingredient quantities (with aggregated nutrition). |
| `meal_plans`, `meal_plan_days`, `meal_plan_slots` | The weekly plan: one active plan → 7 days → meal slots. A partial unique index enforces **one active plan per user**. |
| `lifestyle_plans` | Sleep window + exercise suggestions tied to a plan. |
| `daily_logs`, `meal_logs`, `weight_logs` | What the user logged each day (meals, water, weight). |
| `health_readings` | Blood-sugar / blood-pressure readings (with a CHECK enforcing the right fields per type). |

> The full annotated schema, including every column, index, and constraint, is in
> [`design.md`](./design.md).

## 12. How the AI Meal Plan Is Generated

Plan generation is encapsulated in `server/src/services/planGeneration.service.ts`:

1. **Load context** — fetch the user's `health_profiles` row and their medical conditions.
2. **Compute targets** — derive calorie/macro targets from the profile (see §13). If the trigger
   is a high blood-sugar reading, targets are **tightened** (carbs ×0.85, sugar ×0.70).
3. **Prompt Gemini** — `utils/ai.service.ts` builds a structured prompt describing the user
   (age, sex, weight, goal, activity, conditions, fasting, diet) and the daily targets, and asks
   for a **strictly-JSON** 7-day plan of **Ethiopian** dishes plus a lifestyle block. It tries a
   list of candidate Gemini models for resilience and strips any Markdown code fences before
   parsing.
4. **Persist** — the previous active plan/lifestyle are marked `replaced`, then a new
   `meal_plans` row, a `lifestyle_plans` row, and for each of the 7 days a `meal_plan_days` row
   with four `meal_plan_slots` (breakfast/lunch/dinner/snack) are inserted. Each planned meal's
   ingredients are matched against the `ingredients` table (by Amharic/English name) and linked
   via `meal_items`.
5. **Return** the new `plan_id` and the generated plan data.

If the AI call fails (e.g. missing key, model unavailable), profile save still succeeds and the
response reports `plan_generation_status: "failed"` instead of erroring the whole request.

Read the full plan back via **`GET /v1/meal-plans/current/weekly`**, which reconstructs the
nested `days → slots → meal → items` structure from the relational tables.

## 13. How Nutrition Targets Are Calculated

Implemented in `server/src/utils/nutrition.ts`:

1. **BMR** via Harris–Benedict (sex-specific; `other` uses the male formula).
2. **TDEE** = BMR × activity multiplier
   (`sedentary 1.2`, `light 1.375`, `moderate 1.55`, `active 1.725`).
3. **Goal adjustment** — `lose_weight` −500 kcal, `gain_weight` +500 kcal.
4. **Macros** — default split 20% protein / 50% carbs / 30% fat; for diabetes the split shifts to
   25% / 40% / 35% (lower carb).
5. **Micronutrient caps** — sodium capped at 1500 mg for hypertension (else 2300 mg); sugar
   capped at 25 g for diabetes (else 50 g).

These targets are stored on the profile and drive both the dashboard comparisons and the AI prompt.
